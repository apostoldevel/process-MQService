MQService — обмен сообщениями
-

**Процесс** для **Apostol CRM**[^crm].

Описание
-

**MQService** — фоновый процесс-модуль для фреймворка [Апостол (C++20)](https://github.com/apostoldevel/libapostol). Несёт долговечный обмен сообщениями между узлами по схеме store-and-forward — для звезды из берегового дата-центра и одного или многих судов, связанных ненадёжным, тарифицируемым, отключающимся на недели каналом.

Это замена выведенного процесса `Replication`. Построчный путь отвергнут: он применял входящие записи сырым DML, предварительно сняв триггеры, — то есть в обход слоя сущностей и его хеш-цепочки. MQService применяет входящее только через `ingest` соответствующего класса сообщений — тот проверяет подпись, происхождение и место в цепочке, а не прошедшее проверку отправляет в dead-letter, а не «записывает всё равно».

Модель одной строкой: **журнал в духе Kafka** (чтение не удаляет; позицию держит читатель), **маршрутизация в духе RabbitMQ** (класс события привязан к каналу; приоритет живёт на канале) и **доставка на класс в духе MQTT** (приоритет · гарантия доставки · срок жизни — три независимые оси, а не одна общесистемная настройка) — по **короткому догоняющему сеансу**, а не постоянному сокету. Полное обоснование — в проектном разборе того приложения, что подключает процесс.

> ⚠️ **Состояние — каркас (первая веха этого репозитория).** Что работает сегодня: жизненный цикл процесса, аутентификация apibot и управление на ходу через `LISTEN mq_cmd`. Что **ещё не реализовано**: сам сеанс обмена (сбор пачки, round-trip, применение входящего, подтверждение водяных знаков) — его форму задаёт схема `mq`, и он приходит отдельным шагом. `run_session()` — заглушка: пишет в лог и не трогает базу. Сырого DML **нет нигде**, осознанно.

Основные характеристики:

* Написан на C++20 с асинхронной неблокирующей моделью ввода-вывода на базе **epoll**.
* Подключается к **PostgreSQL** через `libpq`, роль `apibot` (пул соединений helper).
* Аутентифицируется через OAuth2 `client_credentials` с помощью `BotSession`.
* Принимает команды по каналу PostgreSQL `LISTEN "mq_cmd"` — **применяются без перезапуска**: на судне перезапуск процесса это событие, а смена интервала или пауза канала им быть не должна.

### Архитектура

MQService следует паттерну **ProcessModule**:

```
Application
  └── ModuleProcess (generic-оболочка процесса: сигналы, EventLoop, PgPool)
        └── MQService (ProcessModule: только бизнес-логика)
```

Жизненный цикл процесса (обработка сигналов, crash recovery, настройка PgPool, таймер heartbeat) управляется generic-оболочкой `ModuleProcess`. `MQService` содержит только логику обмена.

### Как это работает (сегодня)

```
heartbeat (1 сек)
  └── BotSession::refresh_if_needed()
  └── после аутентификации → статус: running
  └── process_command_queue()          ← разбирает команды из LISTEN "mq_cmd"
  └── mode == paused    → держим, ничего не запускается
      mode == manual    → run_session() только по явному «синхронизировать сейчас»
      mode == automatic → run_session() по интервалу или по «синхронизировать сейчас»
        └── run_session()  ← ЗАГЛУШКА: пишет в лог, обмена ещё нет (придёт со схемой mq)
```

### Режим — меняется на ходу, не перезапуском

| Режим | Когда идёт сеанс |
|-------|------------------|
| `automatic` | по заданному интервалу и по явному запросу |
| `manual` | только по явному «синхронизировать сейчас» |
| `paused` | никогда; канал держится до возобновления |

### Команды по `LISTEN "mq_cmd"`

Полезная нагрузка `NOTIFY mq_cmd, '<payload>'` — либо JSON-объект, либо короткое слово:

```
{"cmd":"mode","mode":"automatic|paused|manual"}   сменить режим
{"cmd":"sync"[,"channel":"<код>"]}                запросить немедленный сеанс
"pause" | "resume" | "automatic" | "manual"       короткая форма смены режима
"sync"                                            короткая форма запроса сеанса
```

Битая нагрузка пишется в лог и игнорируется; процесс продолжает работу.

Конфигурация
-

В блоке `module` профиля приложения:

```json
{
  "module": {
    "MQService": {
      "enable": false,
      "heartbeat": 60000,
      "mode": "automatic"
    }
  }
}
```

| Параметр | Тип | По умолчанию | Описание |
|----------|-----|-------------|----------|
| `enable` | bool | `false` | Включить/отключить процесс. Держать выключенным до появления схемы `mq` и шага с сеансом обмена — включённым без схемы ему нечего обменивать. |
| `heartbeat` | int | `60000` | Такт сеанса, миллисекунды. Настраивается администратором; реальные умолчания по полосам живут на `mq.channel`. |
| `mode` | string | `automatic` | Стартовый режим: `automatic`, `paused` или `manual`. На ходу перекрывается через `mq_cmd`. |
| `max_pending` | int | `256` | Предел очереди команд `mq_cmd`. При переполнении команда **отбрасывается с предупреждением**, а не молча: очередь несёт управление, потерянная команда пишется в лог. |

Также необходимы:

* строка подключения `postgres.helper` (используется для пула `apibot`);
* учётные данные OAuth2 `service` в файле `conf/oauth2/default.json`.
